# RAG 知识库（速记）

> RAG（Retrieval-Augmented Generation）是把"模型不知道的私有知识"喂给它的标准做法。本文按"系统架构 → 关键模块 → 工程化经验"展开，最后附面试速记。
>
> chunk 策略 / 混合检索 / Reranker / HyDE / RAGAS 评估 / 9 个生产事故 → **[RAG 工程化（深文）](/article/ai/rag-engineering)**

---

## 1. RAG 是什么？为什么需要它？

> **一句话**：在调用大模型前，先把相关文档检索出来塞进 prompt，让模型基于这些"证据"回答。

为什么不直接微调？
- 微调成本高、迭代慢；
- 知识天天变（公司文档、产品说明）；
- RAG 可追溯——能告诉用户"答案来自哪个文档"；
- 控制力更强：可以限定知识范围、做权限隔离。

## 2. 标准 RAG 架构

```
                           ┌────────────────┐
                           │   用户问题      │
                           └────────┬───────┘
                                    │
                          ┌─────────▼─────────┐
                          │  Query Rewrite     │  改写、扩展、子查询
                          └─────────┬─────────┘
                                    │
                ┌───────────────────┼───────────────────┐
                ▼                   ▼                   ▼
        ┌────────────┐     ┌────────────┐     ┌────────────┐
        │ 向量检索    │     │ 关键词 BM25 │     │ 元数据过滤  │
        └─────┬──────┘     └─────┬──────┘     └─────┬──────┘
              │                  │                  │
              └─────────┬────────┴──────────────────┘
                        │
                ┌───────▼────────┐
                │  混合排序 / 融合 │ RRF
                └───────┬────────┘
                        │
                ┌───────▼────────┐
                │   Reranker     │ Cross-encoder
                └───────┬────────┘
                        │
                ┌───────▼────────┐
                │  上下文拼接     │
                └───────┬────────┘
                        │
                ┌───────▼────────┐
                │     LLM        │
                └────────────────┘
```

**离线**（建库）和 **在线**（查询）两条流水线。

## 3. 离线流水线：建库

### 3.1 文档接入
来源多样：PDF、Word、HTML、Markdown、Confluence、飞书、企业 Wiki……
**关键点**：保留结构（标题层级、表格、代码块），别把它们 flat 化。

工具：`unstructured`、`MarkItDown`、`docling`、`PyPDF2`、`mineru`（中文 PDF）。

### 3.2 切分（Chunking）

**最容易被低估、却最影响效果**的环节。

| 策略 | 适用 |
| --- | --- |
| 固定字符数（如 800） | 简单文本，baseline |
| 按段落/标题切（结构感知） | Markdown、技术文档 |
| 语义切分（semantic chunking） | 长篇散文 |
| 父子切分（小块检索、大块送入） | 上下文需要更多信息 |
| **滑动窗口 + 重叠**（chunk_overlap=100~200） | 通用 |

经验：
- chunk size 600~1200 token 是甜区；
- **保留来源元信息**：title、section、url、page；
- 表格、代码、公式单独处理；
- 小标题 + 内容**绑在一起**入库（避免内容脱离上下文）。

### 3.3 向量化（Embedding）

| 模型 | 维度 | 备注 |
| --- | --- | --- |
| `text-embedding-3-large`（OpenAI） | 3072 | 通用强，多语言 |
| `voyage-3` / `voyage-large-2`（Anthropic 推荐） | 1024 | 检索质量好 |
| `bge-large-zh` / `bge-m3`（开源） | 1024 | 中文友好，可自部署 |
| `gte-large` / `e5-large` | 1024 | 通用 |

中文场景**强烈推荐 bge-m3**：支持密集 + 稀疏 + 多向量。

### 3.4 索引存储
- **专用向量库**：Qdrant、Milvus、Weaviate、Chroma；
- **传统库扩展**：pgvector、Elasticsearch knn、Redis Stack；
- 选型考虑：规模、过滤能力、集群、成本、混合检索能力。

> 千万级以下 pgvector 完全够用；亿级以上选 Qdrant/Milvus。

## 4. 在线流水线：查询

### 4.1 Query Rewrite（查询改写）
用户问题往往口语化、有指代，直接检索效果差。
- **重写**：把代词补全，"它支持 SSO 吗" → "Anthropic Claude 支持 SSO 吗"；
- **HyDE**（Hypothetical Document Embeddings）：让 LLM 先"假装"写答案，再用答案做检索；
- **多查询拆解**：复杂问题拆成多个子查询并行查。

### 4.2 混合检索

**只用向量召回会漏，必须配 BM25 等关键词检索**：
- 向量擅长**语义近似**；
- BM25 擅长**精确匹配**（产品 ID、专有名词、代码符号）。

融合方法：**RRF（Reciprocal Rank Fusion）**：
```
score(d) = Σ 1 / (k + rank_i(d))    # k=60 是经验值
```

### 4.3 Rerank（重排）

召回阶段拿 top-50 → 用 cross-encoder 精排到 top-5。

| 重排模型 | 类型 |
| --- | --- |
| `bge-reranker-v2-m3`（开源） | 中文优秀 |
| Cohere Rerank | 商用，效果好 |
| Voyage Rerank | 商用 |

**有无 reranker 的差距很大**——召回 top-50 里"对的"那条往往不在前 5。

### 4.4 上下文拼接

```
你是一个公司知识助手，请基于以下资料回答问题。
如果资料中找不到答案，请明确说"不知道"。

<资料>
[1] 来源: docs/billing.md#refund
内容: ...

[2] 来源: faq/payment.md
内容: ...
</资料>

<问题>
我可以申请退款吗？
</问题>

请用引用编号 [1][2] 标注来源。
```

要点：
- 给资料**编号**，便于引用；
- 明确**找不到就说不知道**——RAG 最怕幻觉；
- 标注**来源**——可溯源是 RAG 的核心价值；
- 资料部分用 XML 标签包裹，避免被当成指令执行。

## 5. RAG 评测

### 5.1 评测维度

| 维度 | 指标 |
| --- | --- |
| **检索质量** | Recall@K、MRR、nDCG |
| **生成质量** | 忠实度（Faithfulness）、相关性（Answer Relevance） |
| **端到端** | 业务指标：解决率、点踩率 |

### 5.2 RAGAS / TruLens 等框架可自动打分

经验：先用 50~100 条**人工黄金集**校准，再扩展到 LLM-as-Judge 自动跑。

## 6. 进阶变体

### 6.1 GraphRAG / 知识图谱 RAG
- 把文档抽取成实体 + 关系，构建知识图谱；
- 适合关联推理（"A 项目的负责人是谁的下属？"）；
- 微软开源 GraphRAG，效果惊艳，但成本不低。

### 6.2 Agentic RAG
- 把检索作为**工具**给 Agent 调；
- Agent 自行决定要不要查、查几次、改写查询；
- 见 [Agent 文章](/article/ai/agent)。

### 6.3 Long Context RAG
- 大模型上下文 1M+ 后，能否直接塞全部文档？
- **答案是可以但贵**：1M token 单次成本不低，且**长上下文召回率仍下降**；
- 实战仍需 RAG 做"粗筛"，长上下文做"放大上下文"。

### 6.4 多模态 RAG
- 图片、表格、PDF 截图：
  - 用多模态 embedding（如 CLIP、Voyage Multimodal）；
  - 或先 OCR / VLM 描述再切片入库。

## 7. 工程实战经验

### 7.1 召回不准的常见原因
- **chunking 太碎或太粗**：调 chunk_size + overlap；
- **embedding 模型差**：换模型，重新建库；
- **元数据过滤没做**：库里塞了无关文档；
- **query 太短/太长**：做 query rewrite。

### 7.2 幻觉的防线
- 强 prompt：明确"找不到就说不知道"；
- 引用强制：要求每个事实必须 [N] 引用；
- 后置校验：用规则或 LLM 复核每个声明是否在资料中出现。

### 7.3 权限与隔离
- 元数据加 `tenant_id` / `acl`；
- 检索时强制带上过滤条件；
- 定期回归测试：A 用户绝不能搜到 B 用户的文档。

### 7.4 文档更新策略
- 全量重建：简单粗暴，小库可用；
- 增量索引：用文档哈希追变更，差异更新；
- 软删除：旧版本打 tombstone，避免冷不丁返回过期内容。

## 8. 一份"上线即用"的 RAG 配方

```
chunk_size: 800 tokens, overlap 150
embedding: bge-m3（中文）/ voyage-3（英文）
存储: Qdrant，HNSW，cosine
检索:
  - 向量 top-50 + BM25 top-50
  - RRF 融合（k=60）
  - bge-reranker-v2-m3 精排到 top-5
prompt:
  - 系统: 你是 X 助手，基于资料回答，不知道就明说
  - 资料用 <doc id="1" source="..."> 包裹
  - 要求引用 [1][2]
评测:
  - 离线 100 条黄金集，每周跑
  - 在线点踩、解决率
监控:
  - 检索耗时、reranker 耗时、命中率
  - LLM token、延迟、引用召回率
```

## 9. 高频面试题速记

1. **RAG 解决什么问题？** 用私有/最新知识增强模型，避免微调，可追溯。
2. **chunking 策略？** 结构感知 + 重叠，600~1200 token 甜区。
3. **为什么要混合检索？** 向量管语义，BM25 管精确匹配。
4. **RRF 是什么？** Reciprocal Rank Fusion，多路结果融合。
5. **Rerank 有必要吗？** 有，召回 top-50 里答案常在 top-5 之外。
6. **怎么减少幻觉？** 强 prompt + 引用编号 + 后置校验。
7. **GraphRAG 与传统 RAG 区别？** 用图谱做关联推理。
8. **Long Context 是不是 RAG 终结者？** 不是，仍需 RAG 做粗筛 + 控成本。
