# 系统设计

> 不是"如何设计 Twitter / 短链 / 秒杀系统"的面试模板。这一节要讲的是：**真实生产系统在演进中遇到的设计权衡**。

---

## 为什么单独开这块

系统设计书有两类典型套路：
1. **"教学模板派"**：给一道题（设计 X），按 7 步走（澄清需求 → API → 数据库 → 扩展 → ...），每个组件都套"加一层 LB / 加一层缓存 / 分库分表"。看完就能过 Google L4 面试。
2. **"豪华全景派"**：把所有组件画一张大图（用户 → CDN → LB → 网关 → 微服务 → MQ → 缓存 → DB → 数据仓 → ML），每个箭头一句话。看完什么都没记住。

但你在公司里要回答的是：
- 缓存击穿 / 雪崩 / 穿透的差别是什么、为什么要分别处理
- 限流 / 降级 / 熔断的真实组合在哪些场景失效
- 一次大促从 5K QPS 到 50K QPS 要改哪几处
- 灰度发布在数据库 schema 不兼容时怎么办
- 怎么算容量？怎么压测出"真"瓶颈而不是"伪"瓶颈

这一节按 [桃花岛深度模板](/STYLE) 切，每篇都从**一个真实事故 / 真实演进**入手，把权衡讲透。

## 规划中的深文

### 1. 缓存设计 ✅ 已完成 → [阅读深文](/article/system-design/cache-design)

**核心问题**：你以为加了 Redis 就万事大吉？热 key 把 Redis 单 shard 打爆怎么办？缓存与 DB 一致性怎么保？双删真的解决一切？

**写作骨架（5 层）**：
- **原理推导**：缓存的 4 种失效模式（击穿 / 雪崩 / 穿透 / 一致性）的本质差别；CDN / LocalCache / Redis 三层缓存的协同
- **源码切片**：Caffeine 的 W-TinyLFU 算法；Redis 的 `MEMORY USAGE` 与 LFU 实现；Canal 同步的核心代码
- **实测数据**：双删 vs 延迟双删 vs Canal 三种一致性方案的实测延迟与一致性窗口
- **生产案例**：热 key 打爆单实例（直播间 / 顶流商品）、雪崩前未做随机 TTL、布隆过滤器误判导致击穿、Canal 异常导致脏缓存
- **延伸**：分级缓存、CDN 边缘计算、Cache Warming、Read-Through vs Cache Aside

### 2. 限流降级熔断 ✅ 已完成 → [阅读深文](/article/system-design/resilience)

**核心问题**：Hystrix 已死，Sentinel / Resilience4j 怎么选？熔断阈值怎么定？降级什么时候触发、什么时候恢复？

**写作骨架**：
- **原理推导**：限流（控入口）/ 降级（牺牲非核心）/ 熔断（断开下游）三者的语义差别；电路断路器状态机
- **源码切片**：Sentinel 滑动窗口 + 自适应限流；Resilience4j 的 CircuitBreaker 状态机
- **实测数据**：不同熔断阈值在突发流量下的"误熔断率"
- **生产案例**：熔断器频繁开合（震荡）、降级链断裂（依赖未做幂等）、限流配置错位导致核心被限流
- **延伸**：自适应限流（Netflix concurrency-limits / Sentinel 的 BBR 模式）、Service Mesh 中的熔断（Istio）

### 3. 高可用架构演进 ✅ 已完成 → [阅读深文](/article/system-design/high-availability)

**核心问题**：单机房 → 同城双活 → 异地多活，每一步要改哪些？为什么"异地多活"几乎所有人都吹得多做得少？

**写作骨架**：
- **原理推导**：可用性 9 个 9 的真实代价；单元化（Cell-based）架构的本质；写流量分发与冲突解决
- **源码切片**：阿里单元化路由的核心代码；蚂蚁 OceanBase 的多机房部署
- **实测数据**：不同架构下的 RTO / RPO 对比；单元化后跨单元请求比例的影响
- **生产案例**：双活回切失败、单元化路由错误、数据库双写冲突
- **延伸**：Spanner / TiDB 的全球事务、Aurora Global Database

### 4. 容量规划与压测 —— 怎么算 QPS、怎么压出"真"瓶颈

**核心问题**：业务说"明年 QPS 翻 3 倍"，要扩多少机器？怎么压才能避免"压测通过、生产挂了"？

**写作骨架**：
- **原理推导**：Little's Law、瓶颈识别方法（USE 模型 / RED 模型）、TPC-W 与生产压测的差异
- **源码切片**：JMeter / wrk / vegeta 的负载模型差别；自研压测工具的核心
- **实测数据**：常见压测错误（短链接、固定 think time、数据冷热不分）的偏差大小
- **生产案例**：压测通过但生产慢（数据冷启动）、压测把 DB 主键打坏（自增 ID 超前）、流量回放的隐私问题
- **延伸**：生产流量影子化、混沌工程（Chaos Mesh / Litmus）、SRE 的容量管理

### 5. 灰度发布与配置中心 —— 不停服上线的工程

**核心问题**：金丝雀 / 蓝绿 / 全量分级，每种在数据库 schema 变更时怎么做？配置中心推送一致性怎么保？

**写作骨架**：
- **原理推导**：灰度的几何（按用户 / 按机器 / 按流量百分比）；DB schema 兼容的 expand-and-contract 模式
- **源码切片**：Apollo / Nacos 配置中心的推送实现；ArgoCD 的金丝雀控制器
- **实测数据**：配置全网生效时间、灰度回滚时间
- **生产案例**：DB schema 变更回滚失败、配置推送顺序错乱导致缓存失效、灰度比例配置错误打到 100%
- **延伸**：Feature Flag 系统（LaunchDarkly / Unleash）、SRE 的渐进式发布

### 6. 秒杀系统演进 ✅ 已完成 → [阅读深文](/article/system-design/seckill)

**核心问题**：教学版"秒杀 = 缓存预扣 + 异步落库 + 限流"。但 100K QPS 的真实秒杀里，缓存能不能撑、库存怎么不超卖、订单怎么有序、退款怎么处理？

**写作骨架**：
- **原理推导**：秒杀的 4 个核心矛盾：流量瞬时 / 库存有限 / 订单一致 / 用户体验
- **源码切片**：Redis lua 原子扣减；本地内存预扣 + 批量同步；MQ 异步落库的事务处理
- **实测数据**：不同方案的吞吐 / 超卖率 / 用户感知延迟
- **生产案例**：超卖事故（lua 脚本 vs 单机锁）、订单异步丢失、退款时段库存恢复错乱、黄牛绕过验证码
- **延伸**：腾讯 / 美团 / 阿里的真实秒杀架构演进、风控与反爬
